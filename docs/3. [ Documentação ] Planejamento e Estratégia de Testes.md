# 🗺️ Planejamento e Estratégia de Testes — Marvel

Este documento define a estratégia, o planejamento de qualidade, a análise de riscos e os critérios adotados para garantir a qualidade do produto **Marvel**. Esta estratégia foi desenhada com base em práticas modernas de QA, priorizando a automação inteligente em camadas e a prevenção de defeitos.

---

## 🎯 1. Objetivos de Qualidade

1. **Garantir a Integridade das Integrações (API)**: Validar se as chamadas GraphQL da MarvelApp respondem dentro das especificações e tratam erros de forma amigável.
2. **Assegurar a Experiência do Usuário (Frontend)**: Validar se os fluxos visuais críticos, navegações e seletores na página Marvel Rivals Heroes funcionam sem falhas ou quebras visuais.
3. **Automação Sustentável**: Escrever uma suíte de testes legível por humanos, fácil de manter, rápida de executar e integrada ao fluxo de entrega contínua (CI/CD).

---

## 🏗️ 2. Estratégia por Camadas (Pirâmide de Testes)

Adotamos a estratégia de testes baseada na **Pirâmide de Testes**, distribuindo o esforço de automação de forma eficiente:

```
         /\
        /  \        🔺 UI / E2E (Foco: Modais, Filtros e Fluxos Visuais)
       / UI \       → Testes mais caros, mais lentos, focados na experiência do usuário.
      /------\
     /        \     🔶 API / Integração (Foco: Contratos, Autenticação, Mutations)
    /   API    \    → Testes rápidos, muito estáveis e com grande cobertura de cenários.
   /------------\
```

### 🔶 Camada de API (GraphQL)
* **Objetivo**: Testar a lógica de negócio, autenticação, permissões e contrato de dados.
* **Ferramentas**: Robot Framework + `RequestsLibrary`.
* **Abordagem**: Foco em queries válidas/inválidas, criação e deleção de recursos (mutations) e validação de payloads HTTP/JSON de erro.

### 🔺 Camada de E2E / UI (Frontend)
* **Objetivo**: Validar a interatividade e a renderização do portal público.
* **Ferramentas**: Robot Framework + `Browser Library` (baseada em Playwright).
* **Abordagem**: Foco na abertura de modais críticos (login, download), funcionamento de filtros de heróis por classe (Vanguard, Duelist, Strategist) e responsividade.

## 📊 3. Análise de Riscos e Ações de Mitigação

A priorização de testes é guiada pela matriz de risco, onde:
$$\text{Severidade (Risco)} = \text{Probabilidade} \times \text{Impacto}$$

### 🔴 Riscos Críticos (Alta Probabilidade e Alto Impacto)
1. **Falha Crítica na Autenticação da API**:
   - *Risco*: Usuário ou sistema de testes não consegue se autenticar com token válido ou a API aceita tokens corrompidos.
   - *Ação de Mitigação*: Testes automatizados robustos de autenticação feliz e infeliz integrados na esteira do CI/CD (Quality Gate 1).
2. **Página de Heróis Não Renderizar (Frontend Quebrado)**:
   - *Risco*: Usuário acessa o site e a lista de heróis fica em branco por falha no carregamento dos scripts JS da CDN.
   - *Ação de Mitigação*: Smoke test E2E que valida a visibilidade de elementos-chave da lista de heróis após o carregamento inicial.

### 🟡 Riscos Altos (Média Probabilidade e Alto Impacto)
1. **Quebra de Contrato GraphQL**:
   - *Risco*: O backend da API remove ou altera um campo do schema GraphQL, quebrando as consultas do frontend.
   - *Ação de Mitigação*: Validação automatizada de Schema e contrato na camada de API.
2. **Inconsistência de Filtros (Frontend)**:
   - *Risco*: Usuário clica em "Vanguard" e o site continua listando suportes (Strategist) devido a um bug no JS.
   - *Ação de Mitigação*: Automação de cliques e validações de conteúdo filtrado por classes na camada E2E.

## 🚪 4. Quality Gates (Critérios de Aceitação e Liberação)

Para que uma alteração de código ou nova funcionalidade seja considerada pronta para produção, ela deve passar pelos seguintes portões de qualidade (Quality Gates):

### 🏁 Critério de Entrada
* Código com build limpo.
* Ambiente de testes (Staging/Production) disponível e estável.
* Variáveis de ambiente (`.env` contendo token válido) configuradas na esteira.

### 🏆 Critério de Saída (Quality Gate para Produção)
* **100% dos testes automatizados críticos** (API Auth, Project CRUD, UI Load e UI Filters) passando.
* **Sem bugs críticos ou de alta severidade** em aberto.
* Relatório consolidado gerado pelo Robot Framework (`report.html`) sem falhas críticas.
* Pipeline do GitHub Actions finalizado com status de sucesso.

---

## 🛠️ 5. Abordagem de Automação & Boas Práticas

1. **Separação de Responsabilidades (Page Object / Keywords customizadas)**:
   - As suítes de testes contêm apenas o fluxo lógico do caso de teste.
   - Detalhes de implementação, seletores CSS e URLs ficam isolados nas pastas `resources/` em arquivos do tipo `.resource`.
2. **Segurança de Credenciais**:
   - Armazenamento de segredos via variáveis de ambiente (`.env` localmente e `GitHub Actions Secrets` no CI/CD).
3. **Geração de Evidências**:
   - Captura automática de telas (screenshots) em caso de falha de teste de UI.
   - Log completo da estrutura JSON das requisições e respostas GraphQL para depuração ágil de falhas de API.

## 🧪 6. Independência de Cenários de Testes (Isolamento)

Um pilar fundamental na automação sustentável de testes é a **Independência Estrita entre os Cenários**. Isso garante a confiabilidade dos relatórios e otimiza a depuração de bugs.

### 🔴 O Risco da Dependência (Efeito Cascata / Cascading Failures)
Se o *Cenário B* depender da execução ou do sucesso do *Cenário A* (ex: o Cenário A cria um projeto e o Cenário B tenta alterá-lo usando o mesmo ID), enfrentaremos problemas graves:
1. **Falsos Negativos**: Se o *Cenário A* quebrar por instabilidade de rede, o *Cenário B* também falhará. Isso mascarará o real estado do *Cenário B*, dando a falsa impressão de que a funcionalidade de alteração está quebrada, quando na verdade o problema foi apenas a criação.
2. **Impossibilidade de Execução em Paralelo**: Testes dependentes não podem ser paralelizados (por exemplo, usando ferramentas como `pabot`), pois a ordem de execução se torna rígida.
3. **Flakiness (Instabilidade)**: A ordem física de execução dos testes na suíte pode mudar, fazendo testes passarem em uma máquina e falharem no CI/CD.

### 🏆 Boas Práticas Adotadas para Isolamento
Para garantir que cada caso de teste seja um "átomo" independente, implementamos as seguintes regras na suíte:

* **Massa de Dados Exclusiva**: Cada teste deve criar e gerenciar seu próprio conjunto de dados (ex: usar nomes exclusivos com carimbo de data/hora ou strings aleatórias `Projeto Teste ${RANDOM_STRING}`).
* **Setup & Teardown Limpos (Autolimpeza)**:
  - O que o teste cria, o próprio teste deve apagar no seu bloco de `Teardown`.
  - Usamos `[Teardown]` locais para garantir que, mesmo se o corpo do teste falhar no meio, a keyword de exclusão/limpeza seja executada.
* **Isolamento de Estado de Browser**: 
  - Para testes de frontend, iniciamos um novo contexto do navegador (`New Context`) para cada teste, garantindo que cookies, localStorage e caches não persistam entre execuções.
* **Espera Dinâmica vs. Espera Estática**:
  - **Proibido usar sleeps fixos** (`Sleep 5s`). Eles deixam a suíte lenta e instável.
  - Usamos esperas ativas baseadas em estados de elementos (`Wait For Elements State` ou `Wait Until Keyword Succeeds`).
