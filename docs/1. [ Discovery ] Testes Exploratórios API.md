# Testes Exploratórios — API GraphQL (MarvelApp)

Esta documentação foi elaborada para consolidar os testes exploratórios e o mapeamento técnico da **API da MarvelApp**. O objetivo é que qualquer pessoa do time (desenvolvedores, gerentes de produto ou QA) consiga entender o funcionamento da API, como consultá-la, o que esperar de resposta e os riscos associados.

---

## 🧠 Entendendo o GraphQL (De Forma Simples)

Se você já trabalhou com APIs tradicionais (**REST**), sabe que normalmente enviamos requisições para caminhos específicos (ex: `GET /users`, `POST /projects`). 
No **GraphQL**, a abordagem é diferente:

1. **Endpoint Único**: Todas as requisições (seja para ler, criar ou deletar dados) são enviadas para a mesma URL via método **POST** (no caso da MarvelApp, `https://api.marvelapp.com/graphql/`).
2. **Escolha de Dados**: É você quem diz exatamente quais informações quer receber no corpo da resposta. Se pedir apenas o e-mail do usuário, a API trará apenas o e-mail, otimizando o tráfego de rede.
3. **Tipos de Operações**:
   - 🔍 **Queries**: Usadas para ler informações (equivalente ao `GET`).
   - ⚡ **Mutations**: Usadas para alterar informações (criar, atualizar, deletar, equivalente a `POST`, `PUT`, `DELETE`).

---

## 🔑 Configuração de Autenticação

Para realizar requisições à API, é obrigatório possuir um **Token de Acesso (OAuth2)** gerado na MarvelApp.

- **URL para obter o Token de Desenvolvimento**: [https://marvelapp.com/oauth/devtoken](https://marvelapp.com/oauth/devtoken)
- **Cabeçalho Requerido**: O token deve ser enviado no cabeçalho HTTP da requisição como `Authorization: Bearer <SEU_TOKEN>`.

## 🔬 Cenários de Teste Exploratório Realizados

Abaixo estão detalhados os testes exploratórios práticos, simulando tanto o fluxo feliz (com dados válidos) quanto os fluxos de exceção (erros de autenticação).

### Cenário 1: Autenticação bem-sucedida e consulta de perfil (`user`)
* **Objetivo**: Garantir que com um token válido é possível ler dados básicos da conta do usuário.
* **Status HTTP**: `200 OK`

**Requisição cURL**:
```bash
curl -s -X POST \
  -H "Authorization: Bearer <MARVEL_API_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"query": "{ user { username email } }"}' \
  https://api.marvelapp.com/graphql/
```

**Query GraphQL Enviada**:
```graphql
query {
  user {
    username
    email
  }
}
```

**Resposta JSON Recebida**:
```json
{
  "extensions": {
    "ratelimit": {
      "window_reset": "2026-08-31T01:15:00+00:00",
      "cost": 3,
      "remaining": 29997
    }
  },
  "data": {
    "user": {
      "username": "Maria Eduarda de Lima",
      "email": "eduarda.lem042@gmail.com"
    }
  }
}
```

> 💡 **O que aprendemos aqui?**
> A API retorna metadados sob a chave `extensions`. Notamos um controle de **Rate Limiting** (Limite de Requisições) ativo, indicando o custo da requisição (`cost: 3`), quanto limite resta (`remaining: 29997`) e quando o limite será resetado (`window_reset`). Isso é um ponto importante para testes de robustez.

### Cenário 2: Criação de novo projeto (`createProject` Mutation)
* **Objetivo**: Validar a capacidade de criar um projeto de design na plataforma enviando uma operação do tipo `mutation`.
* **Status HTTP**: `200 OK`

**Requisição cURL**:
```bash
curl -s -X POST \
  -H "Authorization: Bearer <MARVEL_API_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"query": "mutation { createProject(input: {name: \"Projeto Teste Marvel Rivals\"}) { ok project { pk uuid name prototypeUrl isArchived } error { message } } }"}' \
  https://api.marvelapp.com/graphql/
```

**Mutation GraphQL Enviada**:
```graphql
mutation {
  createProject(input: {name: "Projeto Teste Marvel Rivals"}) {
    ok
    project {
      pk
      uuid
      name
      prototypeUrl
      isArchived
    }
    error {
      message
    }
  }
}
```

**Resposta JSON Recebida**:
```json
{
  "extensions": {
    "ratelimit": {
      "window_reset": "2026-08-31T01:16:00+00:00",
      "cost": 9,
      "remaining": 29772
    }
  },
  "data": {
    "createProject": {
      "ok": true,
      "project": {
        "pk": 7518327,
        "uuid": "06e36de6-92de-4d16-887b-3d2a8c3d7cd9",
        "name": "Projeto Teste Marvel Rivals",
        "prototypeUrl": "https://marvelapp.com/prototype/98j66jd",
        "isArchived": false
      },
      "error": null
    }
  }
}
```

> 💡 **O que aprendemos aqui?**
> A criação gera um identificador numérico único (`pk: 7518327`), um identificador universal (`uuid`) e um link público de protótipo (`prototypeUrl`). A operação retorna um campo auxiliar `ok` para indicar o sucesso antes de inspecionarmos o payload do projeto.

### Cenário 5: Autenticação com Token Inválido / Expirado
* **Objetivo**: Testar como o backend lida com falhas de credencial (token corrompido ou expirado).
* **Status HTTP**: `401 Unauthorized` 🔴

**Requisição cURL**:
```bash
curl -i -s -X POST \
  -H "Authorization: Bearer TOKEN_INVALIDO_AQUI" \
  -H "Content-Type: application/json" \
  -d '{"query": "{ user { username email } }"}' \
  https://api.marvelapp.com/graphql/
```

**Resposta JSON Recebida**:
```json
{"errors":[{"message":"OAuth2 token expired or invalid"}]}
```

> 💡 **O que aprendemos aqui?**
> A API da MarvelApp retorna status HTTP `401` quando o token está explícito, porém incorreto. O corpo da resposta traz um array padrão de `errors` informando o problema específico da autorização.

### Cenário 6: Requisição Sem Autenticação (Fallback do Schema)
* **Objetivo**: Simular uma requisição onde o cabeçalho `Authorization` foi esquecido/omitido.
* **Status HTTP**: `400 Bad Request` 🔴

**Requisição cURL**:
```bash
curl -i -s -X POST \
  -H "Content-Type: application/json" \
  -d '{"query": "{ user { username email } }"}' \
  https://api.marvelapp.com/graphql/
```

**Resposta JSON Recebida**:
```json
{
  "info": [
    {
      "message": "Your request was unauthenticated - you are using a limited schema. Authenticate your request to access the full schema.",
      "documentation": "https://marvelapp.com/developers/documentation/authentication/"
    }
  ],
  "errors": [
    {
      "message": "Cannot query field \"user\" on type \"PublicQueries\". Did you mean \"userTest\"?",
      "locations": [
        {
          "column": 3,
          "line": 1
        }
      ]
    }
  ],
  "extensions": {}
}
```

> 💡 **O que aprendemos aqui?**
> 1. Quando enviamos uma requisição **sem token**, a API não responde com 401 direto. Ela redireciona o usuário para um schema limitado chamado **`PublicQueries`** (para consultas públicas).
> 2. Como tentamos buscar o campo `user` (que exige login), e o schema público não possui esse campo, a query falha com um erro de validação sintática (HTTP `400 Bad Request`): *"Cannot query field 'user' on type 'PublicQueries'"*.
> 3. Ela também inclui um campo de `info` explicando que o request está sem autenticação.

### Cenário 7: Limite de Quota de Projetos (Impedimento do Plano Gratuito)
* **Objetivo**: Avaliar a resposta da API ao tentar ultrapassar o limite máximo de projetos ativos da conta gratuita (máximo de 1 projeto).
* **Status HTTP**: `200 OK` 🟢 (Particularidade do GraphQL: erros de validação de negócios retornam HTTP 200 com array `errors` no corpo).

**Requisição cURL**:
```bash
curl -i -s -X POST \
  -H "Authorization: Bearer <MARVEL_API_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"query": "mutation { createProject(input: {name: \"Projeto Excedente\"}) { ok project { pk } } }"}' \
  https://api.marvelapp.com/graphql/
```

**Mutation GraphQL Enviada**:
```graphql
mutation {
  createProject(input: {name: "Projeto Excedente"}) {
    ok
    project {
      pk
    }
  }
}
```

**Resposta JSON Recebida**:
```json
{
  "extensions": {
    "ratelimit": {
      "window_reset": "2026-08-31T02:17:00+00:00",
      "cost": 1,
      "remaining": 29994
    }
  },
  "errors": [
    {
      "message": "User has hit their project quota",
      "locations": [
        {
          "column": 12,
          "line": 1
        }
      ]
    }
  ],
  "data": {
    "createProject": null
  }
}
```

> 💡 **O que aprendemos aqui?**
> 1. **Impedimento Crítico**: O plano gratuito limita a conta a **1 projeto ativo**.
> 2. **Comportamento da Resposta**: O servidor responde com HTTP `200 OK`, mas com a chave `createProject` como `null` e um erro `"User has hit their project quota"` sob a chave `errors`.
> 3. **Estratégia para Automação**: Os testes automatizados que realizam criações (mutations) devem obrigatoriamente deletar o projeto recém-criado no seu bloco de `Teardown` para liberar a quota da conta para o próximo teste ou próxima execução.

## 🎯 Lições e Boas Práticas para a Automação (Robot Framework)

1. **Gestão do Token**: O token deve ser mantido no arquivo `.env` e carregado dinamicamente no Robot via `%{MARVEL_API_TOKEN}`. NUNCA coloque tokens diretamente no código (`hardcoded`) para evitar vazamento de credenciais no GitHub.
2. **GraphQL no Robot**: Como enviamos um JSON via POST com a chave `query`, utilizaremos a biblioteca `RequestsLibrary` com o formato:
   ```robot
   ${body}=    Create Dictionary    query=mutation { deleteProject(input: {pk: ${PROJECT_ID}}) { ok } }
   ${response}=    POST On Session    marvel_api    /graphql/    json=${body}
   ```
3. **Validação de Erros**:
   - Em testes de sucesso: validar se a resposta não possui a chave `errors` no corpo do JSON.
   - Em testes de falha (ex: sem token): mapear o retorno HTTP `400` e a mensagem de erro específica no array de `errors`.
4. **Resiliência / Rate Limits**: Monitorar nas respostas a propriedade `extensions.ratelimit.remaining`. Se aproximar de zero, a suíte de testes deve possuir pausas ou estratégias de repetição.
